# Системные сообщения и маркеры

**Вторая главная путаница у моделей.** Системное сообщение - не оператор.

## 1. Главный инвариант

**Без маркера `[...]` = оператор.** Всё с маркером в начале - системное.

Проверять ПЕРВЫЙ СИМВОЛ сообщения. Если `[` -> системное. Иначе -> оператор.

## 2. Таблица маркеров

| Маркер | Что | Правильная реакция |
|---|---|---|
| `[ALIVE?]` | Watchdog проверяет связь | `[ALIVE] <серия> на связи` (коротко, без воды) |
| `[ACK]` | Подтверждение получения | Не отвечать (это ответ на мой ACK) |
| `[COUNCIL]` | Оператор написал в общий чат | Прочитать chat.jsonl, ответить по существу |
| `[MEETING]` | Кнопка «Совещание» ON | Стоп run/write/sandbox. Режим диалога. Отвечать через `say.py` `>ALL` |
| `[PAUSE-ALL]` | Полная пауза | Ничего не писать. Ждать `[RESUME]` |
| `[RESUME]` | Снятие паузы/совещания | Возобновить работу |
| `[SYS]` | Автоматика (watchdog, guard) | Учесть, не отвлекаться |
| `[X>Y]` | Сообщение от X кому Y | Прочитать, выполнить, отписаться `[Y>X]` |
| `[X>ALL]` | Broadcast от X | Прочитать, использовать, ответить если нужно |
| `[LA>X]` | Вопрос от LocalAI агенту X | Ответить `say.py X "[X>LA] ..." LA` (обязательно `to=LA`) |
| `[AGENT REPORT]` | Отчёт моста на команду | Читать, `next_id`, не отвечать |

## 3. `[ALIVE?]` - разбор

**Что это:** watchdog (per-channel) шлёт раз в interval (300 с), если агент долго молчит.

**Что НЕ надо:**

- Не отвечать развёрнуто («здравствуйте, я на связи, готов к работе»).
- Не путать с вопросом оператора.
- Не игнорировать (иначе watchdog думает, что агент мёртв).

**Что надо:**

```
[ALIVE] 11B на связи, работаю / жду задачу / на паузе.
```

Одна строка. Дальше - работа.

**Если TODO пуст:** короткая реплика + `svc.py stop` (по правилам v5).

**Если TODO не пуст:** вернуться к работе, не «докладывать» про ALIVE.

## 4. `[MEETING]` - совещание

**Что меняется:**

1. Инструменты `run/write/sandbox` - **стоп**.
2. Ответы - только через `say.py X "[X>ALL] ..." ALL`.
3. Маркер `>OP` заменяется на `>ALL` (все видят ответ).
4. Кнопка «Совещание» отжата -> `[RESUME]` -> обычные правила.

**Почему `>ALL`:** на совещании важен каждый ответ для общего контекста. Если писать `>OP` киком - коллеги не увидят.

## 5. `[PAUSE-ALL]` / `[RESUME]`

**PAUSE-ALL:**

- Ничего не отправлять.
- Накопить в буфере (TODO, черновик).
- Ждать `[RESUME]`.

**RESUME:**

- Возобновить с того же места.
- Не переспрашивать «что я делал».

## 6. `[AGENT REPORT]` - не оператор

**Что это:** мост вернул результат на мой блок `op: run|read|write`.

**Что надо:**

- Читать содержимое (stdout, ошибки).
- Использовать `next_id` - следующий блок с новым id.
- **Не отвечать** на отчёт текстом. Это не сообщение от человека.

**Ошибка:** долго ждать ответа от `[AGENT REPORT]` - его не будет.

## 7. Путаница моделей (частые ошибки)

### Ошибка 1: принимает `[ALIVE?]` за вопрос оператора

Плохо: «Да, я жив, спасибо, что спросили! Готов к работе.»

Хорошо: `[ALIVE] 11B на связи, работаю по TODO.`

### Ошибка 2: путает `[X>Y]` с оператором

Плохо: `[A>B]` -> ответ развёрнутый «Уважаемый коллега, спасибо за сообщение...»

Хорошо: `[B>A] Понял, беру в работу.`

### Ошибка 3: отвечает коллеге в свой чат

Плохо: текст `[B>A] ...` написан в моём окне (не через `bridge_kick2.py`).

Хорошо: блок `op: run` с `bridge_kick2.py --port <CDP A>`.

### Ошибка 4: реагирует на `[SYS]` как на команду

Плохо: увидел `[SYS] Format reminder` -> начал паниковать, отвечать текстом.

Хорошо: учесть, исправить (если формат был неверный), продолжить.

### Ошибка 5: копирует `[ALIVE?]` в свой ответ

Плохо: `[ALIVE?] Я на связи` - маркер сохранён, мост думает, что это новый ALIVE-запрос.

Хорошо: `[ALIVE] ...` - маркер ALIVE (не ALIVE?).

## 8. Что делать при получении системного сообщения

1. Определить тип (по маркеру).
2. Вспомнить, что он значит (таблица §2).
3. Действовать по алгоритму (не «беседовать»).
4. Не отвечать развёрнуто, не удивляться, не паниковать.

**Правило:** системное сообщение - **качели**. Тебе дали сигнал - ты сделал шаг. Не «здравствуй, дорогой маркер».
