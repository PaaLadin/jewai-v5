# Replay stale blocks (инцидент 22.10)

**Критичный инцидент.** Прочитать всем, кто трогает content*.js / мост.

## 1. Что было

Агент D 22.10 в 20:xx прислал блок `stop all`. Мост исполнил. Процесс убил себя (stop all включает всех).

Через 2 минуты **тот же блок исполнился снова**. Потом ещё раз.

**Причина:** мост сканировал **всю историю чата**, а не последние сообщения. Старые блоки всплывали и исполнялись повторно.

**Последствия:** хаос, паника, несколько раз "всё умерло".

## 2. Правила (обязательно)

### 2.1. Не сканировать всю историю

**Блоки команд брать ТОЛЬКО из последних ответов модели.**

`SCAN_LAST_MSGS = 3` - только 3 последних ассистентских сообщения.

Иначе старые блоки (например `stop all`) всплывают и исполняются повторно.

### 2.2. In-memory dedupe не переживает reload

**Всё, что защищает от повторного исполнения - в `chrome.storage`, не в переменной.**

При reload страницы память чистится, переменная `seenIds = []` исчезает.

`chrome.storage.local.set({recentlySentIds: [...]})` - переживает.

### 2.3. Леджер исполненного >= 500 записей

`RECENT_LIMIT = 500` - хранить последние 500 id.

Плюс **водяная метка** (watermark) - максимальный исполненный id. Всё `id <= watermark` - SKIP (stale).

### 2.4. `stop all` убивает и сам исполнитель

`stop all` останавливает ВСЕ процессы, включая тот, что его исполняет.

**Выживший Chrome - не виновник.** Не искать "кто выжил", искать "что исполнялось".

### 2.5. Диагностика HTTP обязательна

При странных падениях логировать: `path`, `target`, `UA`, `referer`.

### 2.6. UA различает источник

- **Mozilla** - браузер/панель (человек).
- **Python-urllib** - python-скрипт (автоматика).

По UA видно, кто дёрнул endpoint.

## 3. Реализация в v5 (Bridge/exec.py)

**Replay-guard:**

1. **Единственный водяной знак** - `last_processed_id` в файле (atomic write), не в памяти.
2. **Не только ID, но и хэш содержимого** - блок с тем же id, но другим содержимым тоже не исполняется; пишется в `stale_blocks.log`.
3. **ID-счётчик монотонно вверх** - блок с `id < watermark` помечается SKIP, агенту возвращается `next_id` без исполнения. Явно в отчёте: `SKIP: stale`.
4. **Скан только последних N сообщений** (`SCAN_LAST_MSGS = 3`), при первом запуске после reload - не подхватывать всю историю: инициализировать водяной знак по текущему максимуму id в чате.
5. **Отдельный лог** `logs/bridge/stale_blocks.log` (в v5 - `Profiles/<L>/logs/stale_<L>.log`): timestamp, id, op, hash, длина.

## 4. Проверка (как убедиться, что guard работает)

1. Отправить блок с id X.
2. Дождаться `[AGENT REPORT] OK`.
3. Отправить ещё раз тот же блок (тот же id).
4. Ожидание: `[AGENT REPORT] SKIP: stale` (или `SKIP: dup`).

Если исполняется второй раз - guard сломан.
