# Kick protocol - как агенты общаются

**Главный источник путаницы у моделей.** Прочитать до первого сообщения в чат.

## 1. Три разных способа «написать» - не путать

| Что | Кому доставляется | Кто видит | Транспорт |
|---|---|---|---|
| **Kick в личный чат коллеги** | Только агенту X | Только X | `bridge_kick2.py --port <CDP X>` (A-D) / `bridge_kick3.py` (E/F) |
| **Broadcast в общий чат** | Всем агентам + оператору | Все | `say.py <X> "[X>ALL] ..." ALL` |
| **Kick оператору в личный чат** | Только оператору | Только оператор | POST `/api/chat/<CH>` или `say.py` с `to=OP` |

**Три разных транспорта. Не взаимозаменяемы.**

## 2. Правила выбора

### 2.1. Агент -> агент (p2p)

**Когда:** ответ коллеге на его кик, координация по задаче, вопрос конкретному агенту.

**Маркер:** `[X>Y]` (от X кому Y). X, Y - буквы каналов (A, B, C, D, E, F).

**Транспорт:** ТОЛЬКО `bridge_kick2.py` (A-D) / `bridge_kick3.py` (E/F).

```
python sandbox/bridge_kick2.py --port 9224 --text "[A>C] Семён, вопрос по аудиту"
```

Порт - CDP-порт **получателя** (C = 9224 в старом проекте, в v5 = 9124).

**Что видит C:** сообщение в СВОЁМ чате с маркером `[A>C]`. Оператор НЕ видит.

### 2.2. Агент -> все (broadcast)

**Когда:** доклад в общий чат, объявление для всех, ответ в совещании.

**Маркер:** `[X>ALL]`.

**Транспорт:** ТОЛЬКО `say.py` с `to=ALL`.

```
python sandbox/council_chat/say.py A "[A>ALL] Готово, 21/21 тестов" ALL
```

**Что видят все:** сообщение в общем чате (chat.jsonl), его читают все агенты и оператор.

### 2.3. Агент -> оператор (личный чат)

**Когда:** личный вопрос, доклад «только для оператора».

**Маркер:** `[X>OP]` в старом, `[X>ALL]` в совещании (`>OP` заменяется на `>ALL`).

**Транспорт:** POST `/api/chat/<CH>` или через kick оператора.

**Что видит:** только оператор.

### 2.4. Оператор -> агент

Приходит как kick в личный чат агента или как broadcast в общий.

Агент видит сообщение как обычный текст. Реагирует по контексту.

## 3. Инварианты (нарушение = провал задачи)

1. **P2P не публикуется в общий чат.** Маркер `[A>B]` + `say.py` = ошибка канала.
2. **Broadcast не кикается в один порт.** Маркер `[A>ALL]` + `bridge_kick2 --port B` = ошибка.
3. **Персональный чат - не p2p и не broadcast.** Это отдельный транспорт: POST `/api/chat/<CH>`.
4. **В общий чат не пишем персональные id.** id-формат `Z<CH>AA<NNNN>` только в `/api/chat/<CH>`.

## 4. Признак ошибки (по чему понять, что ошибся)

- **Ждёшь ответа коллеги, а его нет** -> кикнул в свой чат (текст написан в моём окне, а не через `bridge_kick2`).
- **Коллега отвечает «как оператор»** -> кикнул без маркера `[X>Y]`.
- **Оператор говорит «я не видел»** -> отправил p2p вместо broadcast.
- **Коллега не понимает контекст** -> отправил broadcast вместо p2p (увидели все, но не тот, кому надо).

## 5. Кик короткий

**Длинные кики рвутся, доходит первая строка.** Ядро сообщения - в первые 100 символов.

Плохо:
```
[A>B] Привет, у меня тут проблема с аудитом: во-первых, я проверил 29 разделов,
во-вторых, нашёл 8 зон покрытия, в-третьих, есть вопрос про replay-guard...
```

Хорошо:
```
[A>B] Проблема с replay-guard, см. council/threads/A_to_B.md
```

## 6. Кик только при пустой textarea

Перед отправкой: `read_panel_state` - textarea пустая?

- Пустая -> кикаем.
- **Непустая -> НЕ кикаем** (`--wait-empty`, не `--force`). Текст оператора или свой черновик - не трогать.
- Force удалён из `bridge_kick2.py` - его нет.

## 7. Отправка с сервера (не только локально)

При отправке из python-скрипта (не через агента):

1. Вставка текста в textarea.
2. Пауза 0.8 с.
3. Enter 1.
4. Пауза 3 с.
5. Enter 2.

Один Enter в SPA (Qwen, Alice) - не отправляет. Два Enter - канон.

## 8. Как агент в чате отправляет кик (через блок op=run)

Агент в чате (я) **не может** вызывать `bridge_kick2.py` напрямую - у меня нет shell.

Я пишу блок с `op: run` - мост исполняет `bridge_kick2.py` - сообщение летит.

Формат блока:

строка открытия (### BEGIN ###), строки ключ:значение, строка закрытия (### END ###)

Поля:

- `id`: мой префикс + номер (AAAA1001, BBAB2000, ...).
- `op`: `run`
- `cmd`: `python sandbox/bridge_kick2.py --port 9124 --text "[A>C] вопрос"`
- `cwd`: корень проекта.
- `timeout`: 60.

**Важно:** `--text` содержит маркер `[A>C]` - он доедет до C, C поймёт «это от A».

## 9. Куда смотреть если что-то не так

- Лог кика: `logs/kick_dropped.log` (в v5 - `logs/svc/kick.log`).
- `bridge_kick2.py` возвращает `{ok, sent, port}` - смотреть.
- Если `ok: false, reason: "textarea_busy"` - кик не ушёл, textarea занята. Не форсить.
- Если `ok: false, reason: "no_ta"` - не нашёл textarea. Проверить CDP-порт.

## 10. Канон (краткая шпаргалка)

| Надо | Маркер | Транспорт |
|---|---|---|
| Сказать коллеге | `[X>Y]` | `bridge_kick2.py --port <CDP Y>` |
| Сказать всем | `[X>ALL]` | `say.py X "..." ALL` |
| Сказать оператору лично | `[X>OP]` | POST `/api/chat/X` (в совещании `>ALL`) |
| Получил кик от Y | `[X>Y]` | Ответить `[Y>X]` через `bridge_kick2` в Y |

**Без маркера = оператор.** Увидел сообщение без `[...]` - это человек, не коллега.
